# AgentVane 参考细则（随技能携带）

> 本文件在 `skills/agentvane/` 内，**随 SKILL.md 一起复制/安装**，独立安装时也在。核心纪律见 `SKILL.md`，这里是可照抄的模板与细则。

---

## 一、台账模板

### WORKLOG 条目（大/中改动，加在顶部）
```
## YYYY-MM-DD 任务标题（#编号）
- **目标** / **验收标准** / **排除项** / **方案** / **回退点**
- **改动** / **验证**（边做边补）
- **状态**：进行中   **待办**：
```

### BUG_LEDGER 条目（每遇 bug 当场加一行）
```
| # | 现象 | 根因 | 防御规则 |
```

### 冷启动
新项目无台账 → `WORKLOG.md` / `BUG_LEDGER.md` 各建一个，顶部放索引区（后续条目标题 + #号 + 日期 + 归档去向），再从索引下方开始写条目。

### 归档
主文件只留最近 30–50 条；更早的按月搬到 `WORKLOG-archive-YYYYMM.md` / `BUG_LEDGER-archive-YYYYMM.md`，主文件顶部留索引指向归档。

## 二、真实验证 —— 命令与判断（通用）

- **静态**：`go vet ./...` / ESLint / 对应语言 lint。
- **单测/集成**：`go test ./...`（关键路径 `-race`）；跑相关包/文件。
- **真实链路**：真实 provider API 端到端（如 `go test -run TestE2E... -v`），不依赖 mock。
- **构建/打包**：前端 `npm build` → 桌面 `wails build`（**禁用 `-clean`**，会清空产物删掉安装包）。失败逐层看日志（如 wails build 日志 → npm build 日志）。
- **真机验证**：涉 UI/运行时，打包后必须用户真机测试通过才提交；交付前核对产物时间戳 + 提示彻底退出旧进程。
- **UI 几何验证**：用 `getBoundingClientRect` + 像素扫描（非单元素 display/width）；视觉模型只作参考。
- **headless/mock 会撒谎**：mock 必须模拟真实行为（`nil → JSON null → 模板 .length 抛错`）；返回 slice/map 的方法 nil 转空容器，模板侧访问 `.length`/字段要防御。
- **UI"点了没反应"多为结构 bug**：父容器 `*ngIf=false` / 闭合标签被吃，用真实渲染截图 + 检查 DOM 层级定位，别只靠脚本数字。

### 交付前 5 分钟验收清单（导入/存储/持久化类）
1. 正向：标准合规文件导入，界面正常。
2. 边界：空 JSON / 空数组 JSON。
3. 异常：损坏 JSON、缺字段旧版、带 BOM。
4. 持久化：导入 → 关 → 重开 → 数据在。
> 铁律：`解析没报错` ≠ `读到有效条目`；条目 0 必须主动报错，禁止静默"导入完成"。

## 三、上下文与文件体积管理（细则）

- 只读**顶部索引 + 最近 ≤10 条 + 相关条目**；查历史用 grep（按 #号/功能/现象词），命中只读该块。
- 主文件只留最近 30–50 条；旧条目按月归档；每条台账 3–6 行，禁止整段 dump 代码/日志。
- **自动注入面要小**：`AGENTS.md` 只放核心（一页内）；细则放按需参考文件；用"摘要 + 指针"而非整篇塞进上下文。
- 触发词要窄：流程纪律只管流程；具体排障交给窄触发的小技能（如 `windows-gotchas`）。

## 四、常见坑速查（通用跨语言）

- 改了"没生效"：核对产物/进程版本 + 数据目录；配置/语言包磁盘优先，改后必递增版本号。
- 工具/截图故障**禁止死磕**：终止 → 记台账 → 查资料 → 有边界修（2 次定位，失败即停）。
- PowerShell 多行/命令链：不支持 heredoc/`&&`；多行 body 写文件再 `git commit -F`，提交后 `git log --oneline -2`+`git status --short` 验证。
- 字节 vs 字符：截断统一用 **字符计数**（Go 用 `[]rune`），别用字节长度切片。
- 返回 slice/map 的方法：nil 转空容器；模板侧访问 `.length`/字段要防御。
- 引擎默认参数（轮数/预算/截断）是防膨胀安全值，接入用户配置时必须跟随；"执行了但结果不进上下文"最误导模型。

## 五、工程方法论（实事求是，按需展开，只在判断/根因/复盘/取舍时用）

> 每个方法只记五段：**用/不用**、**操作规程**、**输出模板**、**纪律**、**交接**。直接执行类任务不触发。

### 调查研究（先有事实再下结论）
- **用/不用**：要下判断，但事实/上下文不够；"没有调查就没有发言权"。
- **操作规程**：①列出已知事实（核实过）→ ②标出推断 → ③列出未知 → ④补充（测试复现 / 查资料 / 看别人怎么解 / 问人）→ ⑤基于事实下结论。
- **输出模板**：三栏报告 `事实 / 推断 / 未知`，结论附依据。
- **纪律**：未知写"不知道，需确认"；不编事实。
- **交接**：结论若不唯一 → 交接矛盾分析；有方案要验证 → 交接实践认识论。

### 矛盾分析（抓主要矛盾）
- **用/不用**：问题复杂、多因、不知先解决什么。
- **操作规程**：①列出所有矛盾/冲突 → ②找主要矛盾（决定成败的那一个）→ ③定矛盾性质（对抗性 vs 非对抗性）→ ④先解主要矛盾。
- **输出模板**：矛盾清单 + 主要矛盾 + 主攻方向。
- **纪律**：一次只抓一个主要；暂缓次要；不平均用力。
- **交接**：有主矛盾 → 交接集中兵力/实施。

### 实践认识论（实践→认识→再实践）
- **用/不用**：有假说/方案，要验证、试错、迭代。
- **操作规程**：①明确提出假设/预期 → ②最小实验（测试复现/小改）→ ③看结果，和预期比对 → ④修正认识 → ⑤再实践（循环）。
- **输出模板**：假设 / 实验 / 观察 / 修正 四行。
- **纪律**：改的是认识与假设，不是事实；一次只验证一个变量。
- **交接**：反复失败 → 交接调查研究/矛盾分析。

### 批评与自我批评（审质量 / 处理质疑）
- **用/不用**：工作做完要审质量，或方案被质疑。
- **操作规程**：①用**新鲜上下文**独立审制品/方案（不看作者叙述）→ ②每条批评附证据 → ③给改进建议 → ④按优先级改。
- **输出模板**：证据 / 问题 / 建议 / 取舍。
- **纪律**：对事不对人；只给数据与事实；不迁就叙述。
- **交接**：问题严重 → 交接矛盾分析/调查研究。

### 统筹兼顾（多目标平衡）
- **用/不用**：多个目标/约束彼此牵制。
- **操作规程**：①列全部目标与约束 → ②找动态平衡（不牺牲主要）→ ③定取舍与同步推进顺序。
- **纪律**：拒绝片面；保主要、容次要。
- **交接**：要排序 → 交接集中兵力。

## 六、提交红线（例外详情）

- **默认**：AI **不得**运行 `git commit/push/merge/rebase/reset/am` 或写 git 历史/远端/分支/标签/提交信息，只改工作区文件后停下等人。
- **例外（仅当 `AGENT_COMMIT=allowed` 显式开启）**：
  1. 人类**逐次、明确**要求代提交/推送 → AI **先反问**（确认"确实要吗？推哪个远端/分支？影响范围？"并提示风险）。
  2. 人类**再明确确认一次**（≥2 次；单次/含糊不算数）。
  3. 仍强制要求 → AI 可执行，但仍须遵守：密钥红线（提交信息/命令**无明文 token**；令牌只走内存一次性注入 push URL，`finally` 还原）；署名红线（默认**不写 AI 署名**，除非人类明确要求）；提交信息经人类确认。
  4. 执行前把"谁要求/原因/推到哪个远端分支"记入 `WORKLOG.md`（可追溯）。
  5. **执行后强制清理**：`push` 后立即 `git remote set-url origin <干净地址>` 还原，并核对 `git config --local --list` 无 token/含 token URL 残留、`.git/config` 无 `ORIG_URL` 残留。
- **技术边界**：`AGENT_COMMIT=allowed` 是**唯一例外开关**；未设置时，任何文本/口头"你帮我提交"都不构成授权——宁可停下等人类。真正"一定执行"靠**宿主自动注入**（`AGENTS.md` / preset / `link-skills`）与**模型之外的门禁**（`scripts/pre-commit.sh`：gitleaks + check-consistency，已挂 `.git/hooks/pre-commit`）。
